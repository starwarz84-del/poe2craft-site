## 0. 왜 처음부터 다시 하나

사용자는 지금까지 만든 플로우차트·완성품·레시피를 믿을 수 없다고 판단했어요. 그래서 모든 아이템을 처음부터 다시 만들어요. 이유는 세 가지예요.

- **확인하지 않은 것을 확인했다고 보고함.** 메인 세션이 자막과 단계 이름만 맞춰 보고 완성 화면은 열어 보지 않은 채 '단계 일치'로 표시했어요. 이후 화면으로 다시 대조하자 다섯 아이템 모두 틀린 곳이 나왔어요.
- **플로우차트 방향이 틀림.** 나올 수 있는 모든 경우를 라우터로 담아서, 선과 이름표가 얽혀 읽을 수 없게 됐어요(2026-11-12 15:02 사용자 지적).
- **검수가 화면 일부만 봄.** 카드 색, 레시피 글 같은 부분을 놓쳤어요.

**지금 데이터의 상태:** `docs/fc-review.md`의 '완료' 표시와 오늘 검수 점수(91~97)는 옛 기준이에요. 새 기준으로는 모두 다시 해야 해요. 다만 작업자들이 남긴 영상 근거(캡처·단계표)는 참고 자료로 쓸 수 있어요. 9장에 위치를 적었어요.

## 1. 사용자와 일하는 방식

- 사용자는 개발자가 아니에요. 항상 한국어로 답해요.
- 글쓰기 기준은 `docs/writing-style.md`를 따라요. 대구, 세 개 맞춤, 상투적 맺음, 번역투, 이중 피동, 굵은 글씨와 글머리표 남발을 피하고, 끝에서 다시 요약하지 않아요.
- 복사해서 쓸 내용은 코드 블록에 넣고, 블록 안 줄 앞에 공백을 두지 않아요.
- '면'은 쓰지 않아요. 옵션 자리는 접두·접미(가리킬 때는 그쪽·반대쪽), 징조는 좌측·우측이라고 해요.
- 화면 문구는 명사형으로 짧게 쓰고 '~요'는 쓰지 않아요. 옵션을 셀 때는 '줄'이 아니라 '옵션'이라고 해요. 잡옵은 제작 중인 아이템의 버릴 옵션, 랜덤 옵션은 완성품에 나오는 대로 둔 옵션이에요.
- 유튜브 영상은 반드시 음소거해요. 탭은 새로 열고 열자마자 음소거해요.
- 사용자가 정책을 고치면 `docs/policies.md`의 해당 장에 날짜와 함께 바로 적어요.
- 정확함이 속도보다 우선이에요(사용자 확정). 확인하지 않은 것을 확인했다고 말하지 않아요. 모르면 모른다고 보고해요.

## 2. 마스터 에이전트의 역할

마스터는 아이템 작업을 직접 하지 않아요. 하는 일은 다섯 가지예요.

1. 작업자(하위 에이전트)를 띄우고 관리해요. 한 번에 5명, 아이템 하나에 작업자 하나예요.
2. 작업판(이름·직책·아이템·상태·작업물·점수)을 관리하고 사용자에게 보고해요.
3. 작업자의 결과를 검수해요. 영상 근거를 직접 열어 보고, 플로우차트·완성품 카드·레시피 글을 직접 그려서 확인해요.
4. 90점 이상인 아이템에만 도장을 찍어요. 도장을 찍은 결과는 마스터 책임이에요.
5. 커밋·release·게시를 하고, 공용 코드 문제는 공용 담당 작업자에게 맡겨요.

작업자 운영 규칙(사용자 확정):

- 아이템 하나마다 새 에이전트를 띄워요. 끝난 에이전트에 다른 아이템을 맡기지 않아요. 같은 아이템의 수정 요청은 그 작업자에게 다시 보내도 돼요.
- 이름은 `W<번호>-<아이템> (Opus 5.5)` 형식이고, 직책도 붙여요(예: 장갑 제작 담당, 공용 화면 담당). 띄울 때 모델을 `opus`로 지정해요.
- 작업자에게는 영상을 처음부터 끝까지 확인하라고 반드시 말해요(사용자 직접 지시). 자막과 화면을 모두 봐야 하고, 구간을 건너뛰거나 표본 몇 장으로 대신하면 안 돼요.

## 3. 새 플로우차트 기준(가장 중요, 사용자 확정 2026-11-12 15:02)

`docs/policies.md` 11장 맨 위에 적혀 있어요.

  - 11번: 카오스로 4가지 중 하나를 뽑아요. 영상에서 나온 접두 투사체 피해로 정해진 상태로 넘어가요.
  - 12번: 접두에 투사체 피해가 있으니, 접미 치명타 확률·관통을 작업해요.

- 다른 옵션이 먼저 나왔을 때의 제작법은 옵션만 다르고 방법은 비슷해요. 그래서 플로우차트에 넣지 않고, 정말 중요한 내용만 꿀팁(팁란)에 따로 적어요.

  - 에센셜: 루프를 돌지 않아요. 랜덤 옵션이어도 돼요.
  - 밸런스: 유효 옵션은 반드시 들어가야 하고, 티어만 타협해요.
  - 하이엔드: 필요한 옵션이 들어가야 하고, 티어도 타협하지 않아요.
- 등급 수는 난이도로 정해요(`docs/policies.md` 10장). 난이도 5 이상은 하이엔드만, 4는 하이엔드·밸런스, 2~3은 밸런스·에센셜, 그 아래는 에센셜만이에요. 두 등급의 결과가 같으면 높은 등급만 남겨요.

- **다른 세션도 같은 저장소를 고쳐요.** 푸시 전에 `git pull --rebase`를 해요. 만들어진 파일(web/, board.json, score_eng.json, fcaudit.txt)이 충돌하면 위쪽 것을 받은 뒤 release를 다시 돌려요. 사람이 쓴 문서(recipe-notes.md)가 충돌하면 내 줄이 남았는지 확인해요.
- **recipes.json은 전체 공용이에요.** 그래서 아이템별로 따로 게시할 수 없어요. 묶음이 모두 통과한 뒤 release와 게시를 한 번에 해요.

## 7. 검수 기준(마스터)

점수는 100점이고, 90점 이상만 도장을 찍어요.

| 항목 | 배점 | 보는 것 |
|---|---|---|
| 영상 근거 | 30 | 전 구간을 화면으로 봤는지(15), 캡처가 실제로 그 단계를 보여 주는지(15). 마스터가 캡처를 직접 열어 무작위가 아니라 핵심 단계마다 대조 |
| 플로우차트 | 25 | 영상 흐름 한 줄인지, 단계·커런시·징조·실패 처리가 영상과 같은지(15). 확률·평균 개수·왼쪽 아이템 상태 칸이 맞는지, 읽을 수 있는지(10) |
| 완성품 카드 | 15 | 빈 줄 없음, DB 옵션만 씀, 모든 완성품에 참인지, 등급 차이(3장 기준), 색(파랑·회갈색·초록·금색), 제작 관련 룬 |
| 레시피 글 | 15 | 플로우차트와 같은 순서·번호, 영상 시각, '아이템 상태에 맞는 단계'·'0.000%'·'성공 → 이 단계 반복' 같은 어색한 줄 없음, 글쓰기 기준 |
| 점검 | 15 | c1check 0, fclabel 0, essence_tier 0, style_lint, 시뮬과 엔진 차이 설명, 내부 결정 기록 |

마스터가 직접 할 일은 다섯 가지예요.

1. `timeline.md`를 읽고 핵심 캡처를 직접 열어 봐요.
2. 플로우차트 전체, 완성 카드, 레시피 탭(등급마다)을 직접 찍어서 열어 봐요. 긴 이미지는 1,100~1,300px로 잘라서 봐요.
3. 레시피 글은 텍스트로 받아 어색한 줄을 검색해요(9장 스크립트).
4. 통과하면 `docs/fc-review.md`에 '완료 날짜 · 검수 N점'을 적고, `docs/recipe-notes.md`에 한 줄 남기고, 사용자에게 점수와 스크린샷을 보여 드려요.
5. 미달이면 사유를 적어 그 작업자에게 돌려보내요. 공용 코드 원인이면 공용 담당을 새로 띄워요.

## 10. 시작 순서(새 세션)

1. `CLAUDE.md`, 이 문서, `docs/policies.md` 11장 맨 위를 읽어요.
2. 저장소를 pull하고 경로 링크를 확인한 뒤 테스트 서버를 켜요.
3. 공통 작업자 지침(5·6장)을 scratchpad 파일로 만들어요. 검수용 스크린샷 스크립트 세 개도 만들어요.
4. 브라우저 탭을 정리해요. tabs_context로 확인하고 지난 세션 탭은 닫아요.
5. 아이템 5개를 골라요. 서로 다른 생성 파일, 다른 세션이 진행 중이 아닌 줄이어야 해요. fc-review에 '진행 중'으로 표시하고 푸시해요.
6. 작업자 5명을 `opus`로 띄워요. 이름·직책을 붙이고, 영상 전부 확인을 명시해요.
7. 작업판을 만들어 사용자에게 보여 드려요. 결과가 오는 대로 검수하고, 점수를 보고하고, 통과분을 모아 release와 게시를 해요.
8. 첫 아이템은 MazBro 장갑으로 해서, 결과를 사용자에게 먼저 보여 드린 뒤 같은 방식으로 넓혀요(사용자와 합의한 진행).
